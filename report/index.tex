\subsection{Executive Summary}\label{executive-summary}

In global aviation, ground operations (turnarounds) are high-risk
environments where minutes of delay translate to millions in losses, and
safety errors translate to lives.

This project simulates a \textbf{Production Data Pipeline} for ground
audit logs. I engineered a system that ingests \textbf{100,000 raw
flight records}, cleanses them via a \textbf{SQL Silver-Layer}, and
utilizes an \textbf{R-based Validation Engine} to trigger automated
safety alerts when airport performance drifts outside of regulatory
thresholds.

\subsection{Project Architecture}\label{project-architecture}

The engine is built on a modular ``Bronze-to-Gold'' architecture:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Ingestion (Python/SQLAlchemy):} Synthetic generation of 100k
  audit logs with injected ``noisy'' data (outliers, missing values,
  typos).
\item
  \textbf{Transformation (PostgreSQL):} A multi-stage SQL pipeline
  standardizing station codes, resolving entity naming conflicts, and
  calculating performance variances.
\item
  \textbf{Validation (R/Dplyr):} A statistical watchdog script that
  monitors incident rates and flags high-risk stations for immediate
  audit.
\item
  \textbf{Intelligence (Tableau):} An executive-facing dashboard for
  real-time situational awareness.
\end{enumerate}

After initial data profiling, I utilized Common Table Expressions (CTEs)
to transform raw logs into an analysis-ready state and performed a Data
Quality audit which identified 1250 records with missing turnaround
data. This strict filtering logic excludes incomplete records, ensuring
a 100\% complete dataset of flight logs. Key operations included:

\subsubsection{Key Operations}

\begin{itemize}
\item
  Feature Engineering: Turnaround variance and on-time status.
\item
  String Normalization: Trimming and casing codes (e.g., yul
  \(\rightarrow\) YUL).
\item
  Entity Resolution: Merging duplicate vendor names (Menzies Aviation
  \(\rightarrow\) Menzies).
\item
  Outlier Handling: Nullifying turnaround times exceeding 500 minutes to
  prevent skewing KPIs.
\end{itemize}

\subsubsection{4.1 The Performance Spread
(Univariate)}\label{the-performance-spread-univariate}

\subsubsection{Description}

In aviation, averages are deceptive. A station might have an average
delay of zero minutes because one flight was 30 minutes early and
another was 30 minutes late. This query analyzes the Distribution of
Variance to identify our true operational risk: the `Fat Tail' of
extreme delays. Understanding this spread allows operations to move away
from mean-based planning and focus on mitigating cascading delays.

\subsubsection{4.2 The Speed-Safety Tradeoff
(Bivariate)}\label{the-speed-safety-tradeoff-bivariate}

\subsubsection{Description}

A core hypothesis in ground operations is that rushing creates risk.
This query tests that hypothesis by cross-referencing Schedule
Compliance (On-Time vs.~Delayed) with Safety Protocol Breaches. By
isolating flights that beat their target turnaround time, we can
determine if the pressure to hit SLA (Service Level Agreement) targets
is inadvertently incentivizing unsafe behavior on the tarmac.

As turnaround times get shorter (closer to 0), the probability of a
safety breach increases.

\[\rho(\text{Variance}, \text{Incident Rate}) < 0\]

\subsection{5. Automated Validation Engine in

incident rate per station and compares it against a Critical Threshold
(\(2.5\%\)).

\[Incident\ Rate = \frac{\sum Safety\ Incidents}{\sum Total\ Flights} \times 100\]

If any airport (e.g., YUL, LHR) breaches this threshold, the system
triggers a simulated high-priority alert.

The audit cleans data, calculates failure rates, and triggers simulated
alerts.

\subsection{7. Forward Outlook: Enterprise Production
Architecture}\label{forward-outlook-enterprise-production-architecture}

While this portfolio project executes via a localized batch-processing
methodology, it was architected to mirror the logic of a modern
\textbf{Enterprise Data Stack}. In a real-world Ground Operations
scenario, the reliance on flat files (.csv) and manual script execution
is eliminated to ensure real-time situational awareness.

If deployed within an airline's actual tech stack, the pipeline would be
scaled using the following methodologies:

\subsubsection{Orchestration}

(Apache Airflow or cron)

Instead of executing Python, SQL, and R sequentially via a local
terminal, the pipeline would be converted into a \textbf{Directed
Acyclic Graph (DAG)} using Apache Airflow or Prefect.

\begin{itemize}
\tightlist
\item
  \textbf{The Benefit:} Airflow would trigger the ingestion script on an
  automated cron schedule (e.g., every 5 minutes), automatically
  handling retries if the airline's API experiences downtime.
\end{itemize}

\subsubsection{Cloud Data Warehousing}

(Snowflake/BigQuery)

The local PostgreSQL database would be migrated to a cloud warehouse.
The SQL transformation scripts (the Silver Layer) would be orchestrated
using \textbf{dbt (Data Build Tool)}.

\begin{itemize}
\tightlist
\item
  \textbf{The Benefit:} dbt allows for built-in data testing (e.g.,
  automatically asserting that \texttt{turnaround\_actual\_mins} is
  never negative) before the data is passed to the dashboard.
\end{itemize}

\subsubsection{Direct BI Integration}

The intermediate step of exporting \texttt{ground\_ops\_clean.csv} would
be entirely removed. Both the \textbf{Tableau Dashboard} and the
\textbf{R Validation Engine} would maintain secure, live ODBC/JDBC
connections directly to the production tables.

\begin{itemize}
\tightlist
\item
  \textbf{The Benefit:} When the R script identifies a station breaching
  the \(2.5\%\) safety threshold, it can trigger a live webhook (e.g., a
  Slack API or PagerDuty alert) to the on-duty Airport Manager, turning
  a passive dashboard into an \textbf{Active Alerting System}.
\end{itemize}
